## 1. Executive Summary

ลูกค้าใหม่ 100 คน เหลือ 28 คนในงวดถัดไป (−72%) และเหลือ 5 คนเมื่อครบ 6 งวด `[lark]`
คนหายที่จุดเดียวคืองวดที่ 2 ไม่ได้ทยอยหาย — ทุกงวดจึงต้องหาลูกค้าใหม่มาแทนเกือบทั้งฐาน

**สิ่งที่จะสร้าง:** ระบบภารกิจ 3 แกน ที่จ่ายรางวัลเมื่อ **ทำภารกิจสำเร็จ** เท่านั้น `[user]`

|---|---|---|
| FREQUENCY | ซื้อต่อเนื่องกี่งวด + ใช้ Jidrid กี่ประเภท | คนซื้อแล้วหาย |
| VOLUME | ซื้อรวมกี่ใบใน 3 เดือน | ดันฐานราก |
| ENGAGEMENT | Login · ค้นหาเลข · แนะนำเพื่อน · ดู Live (ไม่ผูกกับการซื้อ) | สร้างการรับรู้ feature อื่นในแอป |

## 2. Scope & Mechanic (ยืนยันแล้ว)

### 2.1 กลไกจ่ายรางวัล — MUST

| # | Rule | เหตุผล |
|---|---|---|
| MECH-01 | ทำภารกิจครบเงื่อนไข → ปลดล็อกรางวัลทันที **ไม่เทียบ baseline ย้อนหลัง** | เป็นกลไกที่ทีมยืนยัน `[user]` `[lark]` |
| MECH-02 | ผู้ใช้ **ไม่มี tier status ติดตัว** — "tier" เป็นคำเรียกภายในทีมเท่านั้น ห้ามโผล่ใน UI/copy | ผู้ใช้เห็นแค่ "ภารกิจ" กับ "รางวัล" — ลด cognitive load ตาม value SIMPLIFY `[brand]` |
| MECH-03 | รางวัลต้องกด **claim** เอง ไม่ auto-credit | ต้องมีจุดที่ระบบตัด inventory และผูก consent กับ T&C |
| MECH-04 | 1 ภารกิจ = 1 สิทธิ์ต่อ 1 บัญชี ต่อ 1 รอบแคมเปญ | กันรับซ้ำ |
| MECH-05 | **จุด claim อยู่ที่หน้ารายละเอียดภารกิจเท่านั้น** — ไม่มี tab รวมรางวัลในหน้า mission | `[user 2026-08-06]` · ของที่รับแล้วไปอยู่ในระบบที่มีอยู่เดิม (NokShop / NokPoint) ไม่สร้าง wallet ซ้อน |

### 2.1.1 Reward types — 3 แบบ `[user 2026-08-06]`

| Type | Flow หลัง claim | ปลายทาง |
|---|---|---|
| `PHYSICAL` | กดรับของ → แสดงที่อยู่ที่มีอยู่แล้ว (แก้ได้ ถ้าไม่มีให้กรอก) → กดยืนยัน → **CRM รับเรื่อง** → ทีมจัดซื้อดำเนินการส่งของ | ของส่งถึงบ้าน |
| `E_COUPON` | กด Claim → **redirect ไป My Coupon ใน NokShop** | ใช้คูปองที่ NokShop |
| `NOKPOINT` | กด Claim → เข้าบัญชีทันที | ยอดแต้มใน NokPoint |

**ผลต่อ scope:**
- `PHYSICAL` — fulfillment เป็น **manual ผ่าน CRM + จัดซื้อ** ไม่ใช่ระบบ logistics อัตโนมัติ
- `E_COUPON` — หน้าแสดงคูปองเป็นของ **NokShop ที่มีอยู่แล้ว** ระบบภารกิจไม่ต้องสร้างหน้าคูปองใหม่
- `NOKPOINT` — เป็นแต้มก้อนเดียวกับ NokPoint เดิมในแอป ไม่ใช่สกุลใหม่

### 2.2 Glossary — Jidrid `[user]`

**Jidrid = กล่องสุ่มลอตเตอรี่** ผู้ใช้ซื้อกล่อง ระบบสุ่มใบให้ตามจำนวนที่กล่องกำหนด มี 3 ประเภทตามจำนวนใบ

| ประเภท | จำนวนใบต่อกล่อง |
|---|---|
| `JIDRID_3` | สุ่ม 3 ใบ |
| `JIDRID_5` | สุ่ม 5 ใบ |
| `JIDRID_10` | สุ่ม 10 ใบ |

**JID-01 (MUST)** — "ใช้ Jidrid ≥N ประเภท" = เคยซื้อกล่องสุ่ม **ขนาดที่ต่างกัน** อย่างน้อย N ขนาด — นับ `COUNT(DISTINCT jidrid_type)` ไม่ใช่จำนวนครั้ง `[user 2026-08-06]`

> 🔴 **JID-01 กลับมาเปิดอีกครั้ง 2026-08-23** — Figma `2250:46165` ระบุ **ขนาดกล่องเจาะจง** ต่อ tier ไม่ใช่ "จำนวนประเภท" (ดู §6.1) · ห้ามเขียน rule engine จนกว่า **OPEN-20** จะปิด
**เหตุผล:** เป้าหมายของแกน FREQUENCY คือให้ลองใช้ feature ให้กว้าง ส่วน "ซื้อเยอะ" มีแกน VOLUME รับอยู่แล้ว

ผลที่ต้องยอมรับ: ผู้ใช้ที่ซื้อ `JIDRID_10` ซ้ำ 5 ครั้ง (5,250 บาท) ยังนับเป็น 1 ประเภท → ไม่ผ่าน HARD จนกว่าจะแตะขนาดอื่น

**Consistency check — ใบขั้นต่ำในตาราง §6.1 สอดคล้องกับขนาดกล่องพอดี**

| Tier | เงื่อนไข | ใบที่ derive ได้ | ใบขั้นต่ำในตาราง |
|---|---|---|---|
| EASY | 2 งวด (ไม่บังคับ Jidrid) | 1+1 = 2 | 2 ✓ |
| NORMAL | 3 งวด + Jidrid ≥1 ประเภท | 1+1+**3** = 5 | 5 ✓ |
| HARD | >4 งวด + Jidrid ≥2 ประเภท | 1+1+**3**+**5** = 10 | 10 ✓ |
| VERY HARD | 6 งวด + Jidrid ครบ 3 ประเภท | 1+1+1+**3**+**5**+**10** = 21 | 21 ✓ |

→ ใบขั้นต่ำคือ **ค่าที่คำนวณจากขนาดกล่องที่ถูกที่สุดที่ผ่านเงื่อนไข** ไม่ใช่เลขที่ตั้งขึ้นลอย ๆ — dev ใช้เป็น validation ได้ว่า rule engine คำนวณถูก

### 3.2 Stage 1 — Awareness

**US-101** — As a ลูกค้าที่เปิดแอป, I want เห็นว่ามีภารกิจอยู่, so that ผมรู้ว่ามีอะไรให้ทำก่อนจะปิดแอป

Entry points ที่ต้องรองรับ:

| # | Entry | สถานะใน flow |
|---|---|---|
| ENT-01 | Home → banner "ภารกิจคนจะรวย" | มีใน flow `[flow]` |
| ENT-02 | หน้าบริการ → Icon NokMore | มีใน flow (flow เรียก "Icon ภารกิจคนจะรวย") `[flow]` |
| ENT-03 | Popup / Floating reward เด้งตอนภารกิจสำเร็จ — ได้ทุกหน้าในแอป | **ยังไม่มีใน flow** `[deck]` |

**AC-101**
- Given ผู้ใช้อยู่หน้า Home, When banner แสดงผล, Then กด banner ต้องเข้าสู่ mission entry ภายใน 1 tap
- Given ผู้ใช้อยู่หน้าใดก็ได้ในแอป, When ภารกิจเปลี่ยนสถานะเป็นสำเร็จ, Then แสดง floating reward ที่กดเข้าหน้ารางวัลได้ และปิดได้ด้วยปุ่มปิดที่แตะได้ ≥44×44 px
- Given ผู้ใช้ปิด floating reward, When เปิดแอปครั้งถัดไปในงวดเดียวกัน, Then ต้องไม่เด้งซ้ำสำหรับภารกิจเดิม
- ทั้ง 3 entry ต้องนำไปสู่ decision เดียวกัน: `เข้าภารกิจนี้ครั้งแรก?` `[flow]`

### 3.3 Stage 2 — Onboarding

**US-201** — As a ผู้ใช้ที่เข้าครั้งแรก, I want เข้าใจว่าระบบทำงานยังไงภายในครั้งเดียว, so that ผมไม่ต้องเดาว่าต้องทำอะไรถึงได้รางวัล

**AC-201**
- Given ผู้ใช้เข้า mission ครั้งแรก, When หน้าโหลดเสร็จ, Then แสดง onboarding (bottom sheet ทักทาย + หน้าวิธีใช้งานแบบไล่สเต็ป) `[deck]`
- Given ผู้ใช้เคยเข้าแล้ว, When เข้าอีกครั้ง, Then ข้าม onboarding ไป List ภารกิจทั้งหมดโดยตรง `[flow]`
- Given ผู้ใช้อยู่หน้า onboarding, Then ต้องแสดง **อายุของรางวัล/คูปอง** ตั้งแต่หน้านี้ `[deck]` — เหตุผล: value INTEGRITY กำหนดว่าเงื่อนไขต้องบอกก่อน ไม่ใช่ให้ไปเจอตอนคูปองหมดอายุ `[brand]`
- Onboarding ต้องข้ามได้ และเรียกดูซ้ำได้จากหน้า mission

**US-202** — As a ผู้ใช้ที่ไม่มีภารกิจให้ทำ, I want รู้ว่าทำไมว่าง และรอบหน้ามีอะไร, so that ผมไม่คิดว่าแอปพัง

**AC-202**
- Given `มี Mission = false`, When onboarding จบ, Then แสดง Empty state `[flow]`
- Empty state ต้องมี: เหตุผลที่ว่าง · รอบถัดไปเริ่มเมื่อไหร่ (ถ้ารู้) · ทางออกอย่างน้อย 1 ทางกลับเข้าแอป
- ⚠️ flow ปัจจุบัน Empty state **ไม่มีลูกศรออก** — ต้องกำหนด back path `[flow]`

### 3.4 Stage 3 — Mission feature

**US-301** — As a ผู้ใช้, I want เห็นในการ์ดเดียวว่าภารกิจนี้ต้องทำอะไร ไปถึงไหนแล้ว เหลือเวลาเท่าไหร่ ได้อะไร, so that ผมตัดสินใจได้โดยไม่ต้องกดเข้าไปดู

**AC-301** — Mission card ต้องมีครบ 5 อย่าง `[deck]` `[flow]`
1. ชื่อภารกิจ + รางวัล (มีภาพรางวัล)
2. เงื่อนไขแบบอ่านจบใน 1 บรรทัด
3. Progress `X/Y` เป็นตัวเลขจริง
4. Deadline — เหลืออีกกี่วัน
5. โควตาคงเหลือ ถ้ารางวัลนั้นมีจำนวนจำกัด

- Given ภารกิจมีหลายขั้นย่อย, Then progress bar ต้องแสดง **หมุดระหว่างทาง** ให้เห็นว่าเหลืออีกกี่หมุด `[deck]`
- Given ผู้ใช้ทุกคน, Then เห็นรายการภารกิจชุดเดียวกันทั้งหมด — ไม่มี personalization ในเฟสนี้ `[flow]` `[v0.2]`

**US-302** — As a ผู้ใช้, I want แยกดูภารกิจที่ยังต้องทำ ออกจากภารกิจที่ทำจบแล้ว, so that ผมรู้ว่าเหลืออะไรอีก

**AC-302** `[user 2026-08-06]`
- Tabs: `ทั้งหมด` / `สำเร็จแล้ว` — **ไม่มี tab รางวัล** (MECH-05)
- Given ผู้ใช้กดรับรางวัลไปแล้ว, When เปิด tab `สำเร็จแล้ว` แล้วเข้าภารกิจนั้น, Then หน้ารายละเอียดต้องแสดงสถานะ "รับแล้ว" พร้อม **ทางไปยังปลายทางของรางวัลชนิดนั้น** (My Coupon ใน NokShop / หน้า NokPoint / สถานะการส่งของ)
- **เหตุผลที่ตัด tab รางวัลออก:** แอปมี `สมาชิก → คูปองของฉัน` และ `บริการ → นกพอยต์` อยู่แล้ว การสร้าง wallet ซ้อนทำให้มี 2 ที่เก็บของชนิดเดียวกัน ผู้ใช้ต้องเดาว่าของอยู่ไหน

**US-303** — As a ผู้ใช้ที่ทำเงื่อนไขครบ, I want ได้คะแนน/ปลดล็อกทันที, so that ผมเห็นผลของสิ่งที่เพิ่งทำ

**AC-303**
- Given เงื่อนไขครบ, When ระบบ evaluate เสร็จ, Then สถานะเปลี่ยนเป็น `COMPLETED` และแสดง CTA รับรางวัล `[flow]`
- Given เงื่อนไขยังไม่ครบ, Then กลับไป List และแสดงว่าเหลืออะไรอีก `[flow]`
- Given คะแนนยังไม่ครบตามที่ภารกิจกำหนด, Then แสดงเงื่อนไขที่ยังขาด + preview รางวัลที่รออยู่ `[flow]`
- ต้องระบุ **latency สูงสุดจากพฤติกรรมจริง → progress อัปเดต** และแสดงค่านั้นให้ผู้ใช้เห็น (ดู OPEN-05)

### 3.5 Stage 4 — Follow up

**US-401** — As a ผู้ใช้ที่ทำภารกิจค้างไว้, I want ถูกเตือนว่าเหลืออีกนิดเดียว, so that ผมกลับมาทำต่อ

**AC-401** `[deck]`
- ข้อความต้องมี **ตัวเลขความคืบหน้าจริง** เช่น "อีก 1 งวด" — ห้ามใช้ข้อความลอย ๆ แบบ "อย่าลืมทำภารกิจ"
- ต้องระบุของที่รออยู่ปลายทาง + เวลาที่เหลือ
- CTA เดียวที่กดแล้วไปทำต่อได้ทันที + ปุ่มปิดที่เห็นชัด
- Trigger ต้องผูกกับ **ความใกล้เส้นชัย** ไม่ใช่ schedule รายวัน
- **Frequency cap ต่อผู้ใช้ต่องวด: TBD** — ต้องกำหนดก่อน launch (OPEN-06) · เหตุผล: ค่า default ที่ยิงบ่อยเกินจะทำให้ผู้ใช้ปิดโดยไม่อ่าน และกระทบ trust ซึ่ง value FAIR FOR TRUST ระบุว่าเสียแล้วงานล้มเหลวทันที `[brand]`
- Given `เข้ามาทำภารกิจบ้างไหม? = ไม่`, Then แสดง Modal + CTA ดูภารกิจทั้งหมด `[flow]`

### 3.6 Stage 5 — Reward

**US-501** — As a ผู้ใช้ที่ทำภารกิจสำเร็จ, I want กดรับรางวัลแล้วรู้ทันทีว่าได้อะไร ต้องทำอะไรต่อ, so that ผมไม่ต้องตามหาเอง

**Claim decision chain** `[flow]` `[user 2026-08-06]`

```
CTA รับรางวัล (อยู่บนหน้ารายละเอียดภารกิจเท่านั้น — MECH-05)
 → D6 ยังไม่เคยรับรางวัลนี้?      ไม่ใช่ → สถานะ "รับแล้ว" + ทางไปปลายทางของรางวัลนั้น
 → D7 ยังไม่หมดอายุ และเหลืออยู่?  ไม่ใช่ → "แจ้งหมด / หมดอายุ"
 → D8 reward_type?
      NOKPOINT  → เข้าบัญชีทันที → สำเร็จ
      E_COUPON  → ออกคูปอง → redirect ไป My Coupon (NokShop)
      PHYSICAL  → ยืนยันที่อยู่ → ยืนยัน → CRM รับเรื่อง → รอรับของ
```

**AC-501 — `E_COUPON`**
- Given claim สำเร็จ, Then redirect ไป **My Coupon ใน NokShop** ไม่สร้างหน้าคูปองใหม่ในระบบภารกิจ
- หน้ารายละเอียดภารกิจต้องคงลิงก์ไป My Coupon ไว้ ให้กลับไปหาได้ทีหลัง
- ต้องแจ้งเตือนก่อนคูปองหมดอายุอย่างน้อย 1 ครั้ง `[flow]`
- ✅ ยืนยันแล้วว่า My Coupon ของ NokShop รับคูปองจากภารกิจได้ `[user 2026-08-06]`
- Given claim สำเร็จ แต่ redirect ไม่สำเร็จ, Then ต้องบอกว่า **คูปองออกให้แล้ว** และบอกทางไปหาแบบ manual — claim สำเร็จกับ redirect สำเร็จเป็นคนละเรื่อง

**AC-502 — `PHYSICAL`**
- Given ผู้ใช้กด "รับของ", Then แสดง **ที่อยู่ที่มีอยู่แล้วในบัญชี** เป็นค่าตั้งต้น
- ผู้ใช้ต้องแก้ที่อยู่ได้ในขั้นตอนนี้ และกรอกใหม่ได้ถ้ายังไม่เคยมี
- ต้องแสดงเงื่อนไข **ก่อน** ปุ่มยืนยัน: เงื่อนไขสละสิทธิ์ถ้าติดต่อไม่ได้ · ของหมดแล้วหมดเลย ไม่แลกเป็นเงินสด `[deck]`
- Given กดยืนยัน, Then สร้างเรื่องเข้า **CRM** และแสดงหน้ายืนยันที่บอกว่าจะเกิดอะไรต่อ
- fulfillment เป็น **manual** — CRM ส่งต่อทีมจัดซื้อ ไม่ใช่ระบบ logistics อัตโนมัติ
- ❌ **CRM ส่งสถานะกลับมาแสดงในแอปไม่ได้** `[user 2026-08-06]` → **ไม่มีหน้าติดตามสถานะในแอป** · ผู้ใช้ติดตามผ่าน **LINE OA** แทน

**AC-503 — การสื่อสารเมื่อยังไม่มี SLA** `[user 2026-08-06]`

ระยะเวลาจริงของ CRM → จัดซื้อ → ส่งของ **ยังไม่มีตัวเลขยืนยัน** (OPEN-16) จึงต้องเขียนแบบไม่ผูกวันที่ แต่ห้ามคลุมเครือจนผู้ใช้ไม่รู้จะทำอะไรต่อ

| # | Requirement | เหตุผล |
|---|---|---|
| SLA-01 | **ห้ามแสดงตัวเลขวัน/ระยะเวลาที่ยังไม่ยืนยัน** ในทุกหน้าจอ | ตัวเลขที่เดาแล้วพลาด = ผิดสัญญาโดยตรง · value INTEGRITY `[brand]` |
| SLA-02 | ต้องบอก **สิ่งที่รู้แน่** แทน: ได้รับเรื่องแล้ว · ทีมงานจะติดต่อกลับตามข้อมูลที่ให้ไว้ | ผู้ใช้ต้องรู้ว่าเรื่องไม่ได้หายไปเฉย ๆ |
| SLA-03 | ต้องแสดง **หมายเลขอ้างอิงคำร้อง (CRM ref)** ที่ copy ได้ | ทำให้การสอบถามผ่าน LINE OA ตอบได้เร็ว แทนที่จะต้องไล่ถามว่าใครคือใคร |
| SLA-04 | ต้องมีปุ่มไป **LINE OA** จากหน้ายืนยัน และจากสถานะ "รับแล้ว" ของรางวัลชนิด `PHYSICAL` | เป็นช่องทางติดตามเดียวที่มี |
| SLA-05 | ต้องเก็บ timestamp ตอน CRM รับเรื่อง และตอนของถึงมือ (จาก CRM ฝั่ง manual) | เพื่อ**วัด SLA จริงจากรอบแรก** แล้วกลับมาใส่ตัวเลขในรอบถัดไป — ปิด OPEN-16 ด้วยข้อมูลจริงไม่ใช่การเดา |

**AC-504 — `NOKPOINT`**
- Given claim สำเร็จ, Then แต้มเข้าบัญชี **NokPoint เดิม** ทันที และแสดงยอดใหม่ในหน้ายืนยัน
- ต้องมีทางไปหน้า NokPoint จากหน้ายืนยัน
- แต้มจากภารกิจต้องแยก `reason` ใน ledger ได้ เพื่อ reconcile กับแต้มจากช่องทางอื่น

**AC-505 — โควตา**
- โควตาคงเหลือต้องแสดง **ตั้งแต่หน้ารายละเอียดภารกิจ ก่อนผู้ใช้เริ่มทำ** `[deck]`
- Given โควตาหมดระหว่างที่ผู้ใช้ทำภารกิจอยู่, Then ต้องแจ้งทันทีที่หน้าภารกิจ ไม่ใช่ตอนกดรับ
- การตัดโควตาต้อง atomic — ห้ามแจกเกินจำนวนที่ประกาศไว้ (ดู §5.4)

### 5.2 Mission state machine

```
LOCKED ──► IN_PROGRESS ──► COMPLETED ──► CLAIMED ──► ปลายทางตาม reward_type
              │   ▲            │  │                      ├─ NOKPOINT  → CREDITED
              │   └────────────┘  │                      ├─ E_COUPON  → ISSUED → REDEEMED
              │    refund ถอย     │                      └─ PHYSICAL  → FULFILLMENT_REQUESTED
              │    (SET-03)       │                                        → FULFILLED
              ▼                   ▼
           EXPIRED           EXPIRED / OUT_OF_STOCK
```

| State | เมื่อไหร่ | หน้าจอที่ผูก |
|---|---|---|
| `LOCKED` | ภารกิจยังไม่เปิด หรือยังไม่ถึงรอบ | การ์ด disabled ใน `MSN-201` |
| `IN_PROGRESS` | มี event แรกแล้ว เงื่อนไขยังไม่ครบ | `MSN-210` CTA = "ไปทำภารกิจ" |
| `COMPLETED` | เงื่อนไขครบ (นับเฉพาะ progress ที่ `CONFIRMED`) ยังไม่ claim | `MSN-210` CTA = "รับรางวัล" · `MSN-003` popup |
| `CLAIMED` | claim สำเร็จ ตัด stock แล้ว (QT-01) | `MSN-922` |
| `CREDITED` | `NOKPOINT` เข้าบัญชีแล้ว | `MSN-330a` |
| `ISSUED` → `REDEEMED` | `E_COUPON` ออกโค้ดแล้ว → ผู้ใช้ใช้คูปองที่ NokShop | `MSN-330b` → นอกระบบภารกิจ |
| `FULFILLMENT_REQUESTED` → `FULFILLED` | `PHYSICAL` CRM รับเรื่องแล้ว → ของถึงมือ | `MSN-330c` · **ผู้ใช้ไม่เห็น transition นี้ในแอป** (CRM one-way) |
| `EXPIRED` | หมดเวลาก่อนทำครบ หรือหมดอายุก่อน claim | `MSN-921` |
| `OUT_OF_STOCK` | `stock_left = 0` ก่อน claim | `MSN-920` |

> `PENDING` / `CONFIRMED` (§5.2.1) เป็น**สถานะของ progress record ไม่ใช่ของ mission** — mission ที่มี progress `PENDING` ค้างอยู่ยังคงเป็น `IN_PROGRESS` (SET-01)

| # | Requirement | เหตุผล |
|---|---|---|
| ST-01 | ทุก transition ต้องมี server-side authority — client แสดงผลอย่างเดียว | เป็นระบบที่ผูกกับของมูลค่าสูงสุด 90,000 บาท `[lark]` |
| ST-02 | Evaluation ต้อง **idempotent** ต่อ (user, mission, source_event) | กัน double-grant จาก retry |
| ST-03 | ทุก transition ต้องเขียน audit log ที่ย้อนกลับได้ | value INTEGRITY — ระบบผิดบริษัทรับผิด ไม่มีข้อแก้ตัว `[brand]` |
| ST-04 | `EXPIRED` และ `OUT_OF_STOCK` ต้องมีทางกลับเข้า List | flow ปัจจุบันไม่มี back path จาก edge state `[flow]` |
| ST-05 | `EXPIRED` และ `OUT_OF_STOCK` ต้องเข้าถึงได้จาก `COMPLETED` **โดยตรง** ไม่ใช่ผ่านกันเอง | ของหมดกับหมดอายุเป็นคนละเหตุ เกิดอันไหนก่อนก็ได้ |
| ST-06 | ปลายทางหลัง `CLAIMED` ต้องแยกตาม `reward_type` และเก็บแยกกัน | `CREDITED` จบทันที · `REDEEMED` เกิดนอกระบบภารกิจ · `FULFILLED` เกิด offline (SLA-05 ต้องเก็บ timestamp ทั้ง 2 จุด) |

### 5.2.1 Progress settlement — PENDING / CONFIRMED

**เงื่อนไขบังคับใช้:** เฉพาะกรณีที่การซื้อลอตเตอรี่หรือ Jidrid **ยกเลิก / คืนเงินได้** (ดู OPEN-12 — ถ้าซื้อแล้วจบเลย ข้ามหมวดนี้ได้ทั้งก้อน)

```
purchase event → progress +1 (PENDING)  ← ผู้ใช้เห็นความคืบหน้าทันที แต่กดรับรางวัลยังไม่ได้
                       ↓ พ้นหน้าต่างยกเลิก T+X
                  CONFIRMED             ← นับเข้าเงื่อนไขจริง กดรับรางวัลได้
                       ↑
     refund ก่อน confirm → ถอย progress ออก
```

| # | Requirement | เหตุผล |
|---|---|---|
| SET-01 | Progress ที่ยัง `PENDING` ต้องแสดงให้ผู้ใช้เห็น แต่ห้ามทำให้ mission เข้าสถานะ `COMPLETED` | ให้ feedback ทันทีโดยไม่เปิดช่องรับรางวัลก่อนของ settle |
| SET-02 | ต้องแสดงระยะเวลา settlement เป็นภาษาคนตั้งแต่ onboarding และบนการ์ดภารกิจ | ผูกกับ AC-201 · ตัวอย่างที่ใช้ได้จริง: ShopBack เขียนว่า "ระบบจะอัปเดตสถานะภารกิจประมาณ 3–15 วันหลังคุณช้อป" `[deck]` |
| SET-03 | Refund ก่อน `CONFIRMED` → ถอย progress ออก และถ้าหลุดเงื่อนไขต้องเปลี่ยน mission กลับเป็น `IN_PROGRESS` | ปิดช่อง "ซื้อเพื่อผ่านเงื่อนไข แล้วคืนของ" |
| SET-04 | Refund **หลัง** `CLAIMED` → ไม่เรียกรางวัลคืน แต่ flag บัญชี และนับเป็น abuse signal | ต้นทุนการไล่เก็บสูงกว่ามูลค่าที่ได้คืน · ทำซ้ำถึงระงับสิทธิ์ |
| SET-05 | ค่า **T+X** = TBD (OPEN-12) | ต้องผูกกับหน้าต่างยกเลิกจริงของระบบขาย |

> 🔴 **เงื่อนไข Jidrid เปลี่ยนความหมาย — ขัดกับ JID-01 (§2.2)**
> JID-01 นิยามว่า "ใช้ Jidrid ≥N **ประเภท**" = `COUNT(DISTINCT jidrid_type) ≥ N` (ขนาดไหนก็ได้)
> Figma ระบุ **ขนาดเจาะจง** — NORMAL = กล่อง 3 · HARD = กล่อง 5 · VERY HARD = กล่อง 10

> ✅ **ที่มาของ `% Reward` ชัดแล้ว** — เป็น % ของคอลัมน์ "คิดเป็นเงิน" (ใบขั้นต่ำ × 105) และเป็น **เพดานงบต่อคน ไม่ใช่มูลค่ารางวัล**

## 9. Roadmap

**MVP — งวดแรก**
- ขอบเขต: ENGAGEMENT (สายที่ไม่ผูกกับการซื้อ ความเสี่ยงกฎหมายต่ำสุด) + FREQUENCY ขั้น STARTER/EASY
- ต้องมี: mission list + card (`MSN-200/201/202`), หน้ารายละเอียดภารกิจ (`MSN-210` — จุด claim เดียว), claim flow ของ `NOKPOINT` และ `E_COUPON`, follow-up 1 รูปแบบ, system state ครบชุด `9xx`
- **ไม่มีในรอบนี้:** onboarding (เลื่อนออก — ux §2.2) · tab รางวัล (ตัดถาวร — MECH-05) · `PHYSICAL`
- รันเป็น A/B (มีภารกิจ vs ไม่มี) ตาม R-02
- เกณฑ์ผ่าน: M2 ขยับจาก 0% ไปได้อย่างน้อยครึ่งทางของเป้า 22.5%
- ⚠️ **ขอบเขตกับเกณฑ์ผ่านยังขัดกันอยู่ — ต้องเคาะก่อนเริ่ม (OPEN-18)**

**v1.1 — งวด 2–3**
- เปิด VOLUME ขั้นล่าง (BEGINNER → NORMAL) เท่านั้น + FREQUENCY ครบทุกขั้น
- เปิด reward type `PHYSICAL` พร้อม fulfillment flow เต็ม (`MSN-310/311/330c` + CRM + LINE OA)
- เกณฑ์ผ่าน: M1 ขยับ + ไม่มีเคสแจกเกินโควตา

**v2.0 — งวด 4–6**
- เปิด VOLUME ขั้นบน **ก็ต่อเมื่อ** ตัวกัน R-01 ผ่านรีวิว และ Legal เคลียร์ R-03
- ดูแล LEGENDARY / EXTREME รายคนแบบ manual review
